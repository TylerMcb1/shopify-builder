Shopify Builder — Implementation Plan

1. Product Summary

Shopify Builder is a local desktop application that lets a non-technical user modify Shopify themes using natural-language instructions.

The application wraps Claude Code (via the Claude Agent SDK) behind a controlled GUI. Claude Code runs inside an isolated container and edits a disposable copy of a Shopify theme. Trusted application code on the host handles Shopify authentication, theme retrieval, validation, Git history, previews, and saving changes to unpublished themes. Shopify CLI runs in its own separate container.

Shopify Builder is a Shopify theme harness only. It is not a general coding tool, it does not build Shopify apps, and it does not interact with GitHub or any remote Git service. Git is used purely as a local history and merge engine for theme files.

The application may:

• Create an app-managed unpublished "working copy" of the live theme.
• Save changes to app-managed (or explicitly adopted) unpublished themes.
• Use the live theme as a read-only starting point.
• Show visual previews of changes on a hidden development preview theme.
• Hold a back-and-forth conversation with the user to refine a change.
• Maintain local Git-backed change history.
• Undo changes made to unpublished themes.
• Guide the user through publishing a finished working copy manually in the Shopify admin.

The application must never:

• Modify the live theme.
• Push files to the live theme.
• Publish an unpublished theme.
• Change which theme is currently live.
• Delete themes.
• Give Claude Code access to Shopify credentials.
• Give Claude Code shell, network, or host filesystem access.
• Give the renderer unrestricted shell access.

Going live is always a manual action the user performs in the Shopify admin. The application prepares, checks, and explains; it never presses "Publish".

2. MVP Goals

The MVP must allow the user to:

1. Install the app and complete a guided setup (container runtime, Shopify connection, Anthropic connection).

2. Connect one Shopify store.

3. Create an app-managed working copy of the live theme (default workflow).

4. Optionally create additional named copies, or adopt an existing unpublished theme after explicit confirmation.

5. Describe a change in plain language and refine it through a conversation.

6. See a visual preview (screenshots plus a preview link) after each step of the conversation.

7. Approve or decline edits to sensitive theme files through a clear pop-up.

8. Have validation problems repaired automatically, within a bounded number of attempts.

9. Save the finished change to the selected unpublished theme.

10. Review local change history.

11. Undo any application-created change on an unpublished theme.

12. Run a "Get ready to go live" check and follow step-by-step instructions to publish manually in Shopify.

3. Non-Goals

The MVP will not support:

• Publishing themes from the app.
• Changing the live theme.
• Deleting themes.
• Editing checkout.
• Managing products, collections, orders, customers, or payments.
• Installing or removing Shopify apps.
• Building Shopify apps or any non-theme software.
• GitHub integration, Git remotes, or pushing Git history anywhere.
• Editing third-party credentials or integrations.
• Multi-store management.
• Cloud synchronization.
• Team collaboration.
• Mobile support.
• Fully autonomous deployment.
• Arbitrary terminal access.

4. Recommended Technology Stack

Desktop shell

• Electron
• Electron Builder
• TypeScript

Electron is preferred because the trusted orchestration layer (container runtime control, Git, file intake, previews) is naturally written in the Node-based main process.

Frontend

• React
• Vite
• TypeScript
• Tailwind CSS
• Radix UI primitives or shadcn/ui
• Lucide icons
• Zustand for lightweight UI state
• TanStack Query for request/response data (theme lists, history), updated by pushed job events

Local orchestration (host, trusted)

• Electron main process
• Typed IPC contracts with a push-based job event channel
• Zod validation for all IPC input and all container output
• Execa for controlled invocation of the container runtime CLI (argument arrays only)
• Dugite (bundled, pinned Git binary) for local Git history, diffing, merging, and reverting
• SQLite for durable structured state

Container runtime

• Podman (preferred: rootless, daemonless, free to use)
• Docker (supported fallback)
• A single runtime adapter hides the differences between the two

Bundled, pinned tool images

• Agent image: Node.js plus a pinned Claude Agent SDK version (which ships its own pinned Claude Code), plus the small agent runner.
• Shopify image: Node.js plus a pinned Shopify CLI version (Theme Check is included as the "shopify theme check" command).
• Egress proxy image: a tiny allowlisting HTTPS proxy (for example tinyproxy) used only by the agent container.

All three images are built from a shared slim base so layers are shared and downloads stay small. Images are referenced by immutable digest, never by a floating tag.

Secure storage

• Electron safeStorage (backed by macOS Keychain, Windows DPAPI/Credential Manager, or Linux libsecret/KWallet)
• On Linux, if safeStorage reports the plaintext "basic_text" backend, the app refuses to store secrets and shows remediation steps.

Credentials must never be stored in plaintext project files, logs, Git commits, container images, container configuration, or renderer state.

5. High-Level Architecture

Electron Renderer
  |
  | Typed, restricted IPC (requests + pushed job events)
  v
Electron Main Process (trusted host)
  |
  +-- Setup and tool-readiness service
  +-- Container runtime adapter (Podman / Docker)
  +-- Store and credential service (safeStorage)
  +-- Shopify write gateway (the only path to any Shopify write)
  +-- Theme ownership registry (working copies, adopted, preview, retired)
  +-- File intake service (validates every file entering trusted storage)
  +-- Git history service (Dugite, host only)
  +-- Validation service (Theme Check baseline comparison)
  +-- Change session manager (conversation, turns, approvals)
  +-- Job runner and event bus
  +-- Preview and screenshot service (hardened hidden browser window)
  +-- Local application database (SQLite)
  |
  +--> Agent container        (Claude Agent SDK; no Shopify access, no shell, no open network)
  +--> Egress proxy container (allows the agent container to reach the Anthropic API only)
  +--> Shopify container      (Shopify CLI; short-lived, one command per run)

Trust boundaries

The application has five security zones:

1. Renderer

  • Displays data and collects user actions.
  • Cannot run arbitrary commands.
  • Cannot access credentials directly.

2. Trusted main process (host)

  • Owns credentials, theme ownership records, and the deployment policy.
  • Validates every IPC request and every message coming out of a container.
  • Is the only zone that touches the Git store or the canonical theme files.
  • Executes only allowlisted container runtime commands.
  • Rechecks theme safety before every Shopify write.

3. Agent container (untrusted)

  • Contains the Claude Agent SDK and the agent runner.
  • Sees only a disposable copy of the theme, mounted at a single workspace path.
  • Has no Shopify CLI credentials, no Git store, no host home directory, and no container runtime socket.
  • Has no direct network access; its only route out is the egress proxy, which permits the Anthropic API only.
  • Returns file changes (left in the workspace) and structured events to the host.

4. Shopify container (trusted code, short-lived)

  • Contains a pinned Shopify CLI.
  • Receives the Shopify credential only for the duration of a single command, over standard input.
  • Never sees the agent workspace or the Git store.
  • Is started by the Shopify write gateway with an argument list the gateway builds itself.

5. Egress proxy container

  • Sits on two networks: an internal network shared with the agent container, and the normal outbound network.
  • Permits HTTPS CONNECT to the Anthropic API host(s) only. Everything else is refused and logged.

6. Container Isolation Architecture

Design goals

• Claude Code can only read and write theme files in a disposable workspace.
• The code that holds Shopify credentials and talks to Shopify never shares a filesystem with Claude Code.
• Git history is never reachable from any container.
• Low infrastructure overhead: one container runtime, three small images, no orchestration platform, no compose files required at runtime, no always-on services.

6.1 Why files move by copy, not by shared mounts

The host is the broker between zones. Files only move between zones through the host's file intake service, which copies files and checks every one of them. No directory is ever mounted into both the agent container and the Shopify container.

Host data layout (under the Electron user-data directory)

stores/<store-id>/
  themes/<theme-id>/
    history.git/      Git directory. Host only. Never mounted into any container.
    canonical/        Git working tree (trusted theme files). Host writes it only after intake checks.
                      Mounted read-only into the Shopify container for push and Theme Check.
    inbox/            Empty directory per pull. Mounted read-write into the Shopify container only during "theme pull".
  sessions/<session-id>/
    workspace/        Disposable theme copy. Mounted read-write into the agent container only.
    agent-state/      Claude Agent SDK session files, so a conversation can resume after an app restart.
                      Mounted into the agent container only.

Separate Git container decision

A dedicated Git container is not required. The Git directory lives outside every working tree and is never mounted anywhere, so no untrusted process can read or tamper with it. Git only ever operates on the canonical tree, which contains files that already passed intake. Running Git on the host with the bundled, pinned Dugite binary and hardened settings (Section 11.6) gives the same isolation with less overhead. If a future requirement needs Git to run on untrusted content, the same runtime adapter can run it in a fourth container without changing the rest of the design.

6.2 Agent container

Lifetime

• One agent container per change session. It starts when the session starts, stays alive across conversation turns, and is removed when the session is saved, discarded, or idle beyond a timeout.
• If the app restarts, a new container resumes the conversation from agent-state.

Mounts

• workspace/ read-write at the single workspace path.
• agent-state/ read-write for SDK session files.
• Application policy files (system instructions, allowed-path list, sensitive-file list) read-only from the image itself.
• Nothing else. Never the host home directory, the Git store, canonical/, inbox/, or the container runtime socket.

Runtime restrictions

• Runs as a non-root user (user-namespace mapping on Podman, explicit user ID on Docker).
• Read-only root filesystem with a small temporary scratch area.
• All Linux capabilities dropped, no-new-privileges set.
• CPU, memory, and process-count limits.
• Attached only to the internal network; outbound traffic must go through the egress proxy.
• Claude Code non-essential traffic (telemetry, error reporting, update checks) disabled through its documented environment settings.

Credentials

• The Anthropic credential is stored in safeStorage on the host and handed to the agent runner over standard input as the first protocol message when the container starts. It never appears in the container's configuration, image, or command line.
• No Shopify credential ever enters this container.

Claude Agent SDK configuration (enforced by the agent runner)

• Allowed tools: file read, file write, file edit, file glob, file search, plus two app-defined tools: "ask the user a question" and "report the result of this step".
• Disallowed tools: shell/Bash, web fetch, web search, notebook editing, sub-agent spawning, and any MCP servers other than the app-defined ones.
• Project settings and instruction files found inside the workspace (for example CLAUDE.md or .claude/ folders) are never loaded. Only application-provided instructions are used.
• Every tool call passes through a permission check that rejects any path outside the workspace or outside the allowed theme paths, and pauses for user approval on sensitive files (Section 9.4).
• Turn limits and a per-step time limit stop runaway sessions.

Agent runner protocol

• The host talks to the agent runner through the container's standard input and output using line-delimited JSON messages.
• Host to runner: start, user message, approval decision, question answer, repair request, cancel.
• Runner to host: progress, assistant message, approval request, question, step result, error.
• The host treats every runner message as untrusted. Each message is validated against a schema; anything malformed ends the session safely.
• The runner's path checks are a convenience and an early warning. The authoritative enforcement is the host's file intake (Section 13), which runs regardless of what the runner reports.

6.3 Shopify container

Lifetime

• One short-lived container per Shopify CLI command, removed automatically when the command finishes. No long-running Shopify process exists.

Mounts by command

• List themes: no mounts.
• Pull theme: a fresh empty inbox/ directory, read-write.
• Push theme: canonical/, read-only.
• Theme Check: canonical/ (or a candidate tree, see Section 13), read-only, plus the application's own Theme Check configuration, read-only.

Network

• Normal outbound network for commands that talk to Shopify.
• No network at all for Theme Check, which runs offline and without any credential.

Credentials

• The Shopify credential is passed to a small entrypoint over standard input. The entrypoint places it in the Shopify CLI process environment only, closes standard input, and runs the CLI non-interactively. The credential never appears in the container command line, the container configuration, or the image.

Runtime restrictions

• Same non-root, dropped-capability, no-new-privileges, read-only root filesystem, and resource limits as the agent container.
• Shopify CLI analytics disabled; the CLI is forced into non-interactive (CI) mode so any confirmation prompt fails closed.

6.4 Egress proxy container

• Started on demand when the first agent session begins; stopped when no sessions remain.
• Configured with deny-by-default filtering and an allowlist containing only the Anthropic API host(s), port 443.
• Refused requests are logged as structured events so unexpected exfiltration attempts are visible.

6.5 Runtime setup and overhead

• The setup screen detects Podman first, then Docker.
• If neither is installed, the app explains in plain language why it is needed and opens the official Podman installer download page.
• On macOS and Windows the app initializes and starts the Podman virtual machine automatically and keeps the user-data directory inside the VM's default shared paths.
• The three images are pulled by digest on first run, with a progress bar. A future option can ship image archives with the installer for offline first-run.
• Networks (the internal agent network) are created once and reused.
• The host never mounts the Podman or Docker control socket into any container.

7. Core Workflow

7.1 Application startup

1. Load local settings.
2. Verify the container runtime is installed and running (start the Podman VM if needed).
3. Verify the three pinned images are present and match their expected digests.
4. Verify the Shopify connection (Shopify container, list themes).
5. Verify the Anthropic connection.
6. Fetch the current theme list and classify every theme using the role allowlist (Section 8).
7. Detect role changes since last run (for example, a working copy that the user has published manually) and update the ownership registry.
8. Display the home screen.

The application shows actionable, plain-language setup instructions if any check fails.

7.2 Working copy model (default workflow)

The working copy is an unpublished theme that the app creates and manages. Changes build up on it over time. When the user is happy, they publish it themselves in Shopify.

Creating the working copy

1. User clicks "Create my working copy".
2. Main process refreshes the theme list and identifies the live theme by immutable ID.
3. Check the store's theme count. If the store is at its theme limit, stop and explain how to free a slot in Shopify (the app never deletes themes).
4. Shopify container pulls the live theme (read-only operation) into inbox/.
5. File intake copies the pulled files into canonical/.
6. Git records a "sync" commit on the shopify branch, tagged with the live theme ID it came from.
7. Theme Check runs to create the baseline (Section 13.3).
8. Shopify gateway creates a new unpublished theme named, for example, "[Builder] Working copy" and pushes the files.
9. The new theme ID is read from the CLI's structured output and saved in the ownership registry immediately, before any other step, as kind "working copy", created by the app, with the live theme ID recorded as its origin.

Named copies (advanced)

• Same flow, with a user-supplied or generated name, for example "[Builder] Holiday sale - 2026-10-07".

Adopting an existing unpublished theme (advanced)

• The user can choose an unpublished theme the app did not create.
• A confirmation dialog explains: "Shopify Builder will be able to save changes to this theme."
• On confirmation, the theme is recorded in the ownership registry as kind "adopted". Until then it is available only as a read-only base.

7.3 Change session (conversation)

1. User selects the target theme (the working copy is pre-selected) and types a request.
2. Main process refreshes the theme list and confirms through the Shopify gateway that the target is writable.
3. Host checks out a new session branch from the target's shopify branch and copies canonical/ into a fresh session workspace.
4. In the background, the preview theme is synchronized to match the session's starting point (Section 7.4).
5. Agent container starts with the workspace mounted and receives the request.
6. Claude works. It may ask the user clarifying questions, which appear as chat bubbles with optional quick-reply choices.
7. If Claude tries to edit a sensitive file, the session pauses and the sensitive-file pop-up appears (Section 9.4).
8. When Claude reports the step result, the host runs file intake on the workspace (Section 13).
9. Accepted files are copied into a candidate tree and Theme Check runs against the baseline.
10. If Theme Check reports new blocking problems, the automatic repair loop runs (Section 9.5).
11. On success, the candidate files are written to canonical/ and Git records a "turn" commit on the session branch.
12. The changed files are pushed to the preview theme.
13. Screenshots are captured and shown next to Claude's plain-English summary.
14. The user either replies with a follow-up request (back to step 6), clicks "Undo this step", clicks "Save to theme", or clicks "Discard".

7.4 Visual preview

Non-technical users review the result visually, not as code.

Preview theme

• The app keeps one hidden development theme per store as its preview theme. Development themes are never live and do not appear as normal choices in the Shopify theme library.
• It is created through the Shopify gateway, its ID is recorded in the ownership registry as kind "preview", and it is the only development-role theme the app will write to.
• At session start the preview theme is fully mirrored to the session's starting files. After each successful turn only the changed files are pushed.
• If Shopify has removed the preview theme (development themes can expire when inactive), the app creates a new one.
• Fallback: if the store or credential cannot use development themes, the app uses a single app-managed unpublished theme named "[Builder] Preview" for the same purpose.

Screenshots

• After each successful turn, a hidden, hardened Electron window loads the preview URL (constructed by the main process from the store domain and preview theme ID).
• The window captures desktop-width and mobile-width screenshots.
• Pages to capture default to the home page. Claude's step result may suggest affected page types (home, product, collection, cart, other template); the app maps these to known store URLs and ignores anything else.
• "Before" screenshots of the same pages are taken once from the session's starting theme, so the user sees before and after side by side.
• For password-protected stores, the user enters the storefront password once. It is stored in safeStorage and submitted only by the capture window.
• An "Open preview in browser" button opens the same URL externally.

The code diff remains available under an "Advanced: show file changes" expander.

7.5 Saving a change to the theme

1. User clicks "Save to theme".
2. Job runner takes the per-theme lock.
3. Shopify gateway fetches a fresh theme list and verifies the target is writable (Section 8).
4. Drift check: the target is pulled fresh into inbox/ and compared with the last sync commit (Section 12).
5. If Shopify-side changes overlap with this session's files, Git merges them into the session branch. A clean merge re-runs Theme Check and refreshes the preview, then asks the user to confirm again. A conflicting merge stops the save with a plain-language explanation and options.
6. Shopify gateway pushes only the files this session changed, without deleting anything remote.
7. Shopify gateway re-fetches the theme list and confirms the target is still unpublished (Section 8.4).
8. Git squash-merges the session branch into the shopify branch as a single "change" commit, so each saved change can be undone as one unit.
9. A change record is written to SQLite.
10. Success screen shows the theme name, preview button, "Make another change", and "Undo this change".

7.6 Going live manually (publish workflow)

The app never publishes. Instead it gets the user ready and hands off to Shopify.

Step 1 — "Get ready to go live" check

The user clicks "Get ready to go live" on a working copy. The app runs, read-only:

• All changes saved: no open session with unsaved steps.
• Theme Check passes with no new blocking problems against the baseline.
• Live-theme sync check: the current live theme is pulled read-only and compared with the live snapshot the working copy was created from. This catches edits the merchant made to the live theme after the working copy was created (for example, theme editor settings, new app blocks, or translated text). Publishing the working copy without bringing those in would silently undo them.
• Fresh preview screenshots of key pages.

Step 2 — Bring in live changes (only if the sync check found differences)

• Git performs a three-way merge: the original live snapshot as the common ancestor, the current live theme as one side, and the working copy as the other.
• Clean merge: the result goes through the normal change flow (intake, Theme Check, preview, user confirms, save to working copy). The new live snapshot becomes the working copy's new origin.
• Conflicts: the app lists the affected files in plain language and offers "Keep the live store's version of these files" or "Keep my working copy's version". Either choice goes through the normal preview and save flow. The user never edits merge markers.

Step 3 — Manual publish instructions

• A checklist screen shows each check as passed.
• Step-by-step instructions explain how to publish in Shopify: open Online Store, then Themes, find the theme by name, open its menu, and choose Publish.
• An "Open Shopify Themes page" button opens the store's Shopify admin themes page in the user's browser. The app performs no publish action itself.

Step 4 — Detecting the swap

• The app refreshes the theme list on window focus and every few minutes while open.
• When an app-managed working copy's role changes to live, the app shows "Your working copy is now live."
• The newly live theme becomes read-only in the app, like any live theme, and is marked "retired" in the ownership registry.
• The previously live theme (now unpublished) is labeled "Previous live version (kept for rollback)" and is read-only by default, even if the app originally created it. The app explains that the user can republish it manually in Shopify to roll back.
• The app offers "Start a new working copy". The new working copy's Git repository starts from the retired theme's history, so change history stays continuous across publish cycles.

Why this works

• Only unpublished themes the app created or the user explicitly adopted can ever receive saves.
• The live theme, retired themes, and rollback themes are always read-only.
• The user controls the moment of going live in Shopify's own interface.
• The live-theme sync check prevents a publish from silently undoing changes made to the live theme in the meantime.
• One working copy at a time keeps the store well under its theme limit.

7.7 Undo

Undo a step inside a session

1. User clicks "Undo this step".
2. Host resets the session branch to the previous turn commit and restores the workspace to match.
3. The reverted files are pushed to the preview theme and screenshots refresh.
4. Claude is told the step was undone and that the files were restored.

Undo a saved change

1. User picks a change from history and clicks "Undo this change".
2. Host creates an undo session branch and asks Git to revert that change's single commit. This works for any saved change, not only the most recent.
3. If the revert conflicts because later changes depend on it, the app explains which later changes must be undone first.
4. Intake, Theme Check, and preview run as for any change.
5. The user reviews before-and-after screenshots and confirms.
6. The save flow in Section 7.5 runs, including the drift check and the target checks.

Creating a working copy cannot be undone by the app, because the app never deletes themes. The app explains how to delete the theme in Shopify if the user wants to.

8. Live-Theme Safety Policy

Live-theme protection is an application invariant, not merely a UI feature.

8.1 Deny-by-default role allowlist

A theme may receive a write only if all of the following are true at the moment of the write:

• Its Shopify role is exactly "unpublished" and it is recorded in the ownership registry as a working copy, named copy, or adopted theme, and it is not marked retired; or
• Its Shopify role is exactly "development" (or the fallback preview theme is unpublished) and it is recorded as the app's preview theme, and the write is a preview push.

Every other role (main/live, demo, locked, archived, or any role Shopify adds in future) is read-only. Missing, duplicated, or ambiguous theme IDs are rejected. Theme names are display values only; targets are always resolved by immutable theme ID.

8.2 Single chokepoint: the Shopify write gateway

• Every Shopify write (create theme, push to theme, preview push) goes through one gateway module in the main process.
• The gateway is the only code allowed to start a Shopify container for a write command.
• For every write, the gateway itself fetches a fresh theme list, applies the allowlist in Section 8.1, and builds the full argument list. Callers pass only a change ID or session ID, never flags or raw theme IDs.
• Checks in the UI (filtered pickers, disabled buttons) are convenience only. Security comes from the gateway.

8.3 Mandatory safeguards

• Filter the live theme, retired themes, and non-owned themes out of save-target selectors.
• Permit the live theme only as a read-only base or comparison source.
• Never invoke a theme-publishing command.
• Never pass the Shopify CLI flag that allows writing to the live theme ("--allow-live").
• Run the Shopify CLI non-interactively with standard input closed, so if the CLI ever asks for confirmation to touch the live theme, the request fails instead of proceeding.
• Never delete remote files or themes.
• Do not expose a generic command-execution IPC endpoint.
• Keep Shopify credentials out of the agent container entirely.
• Maintain a strict command and argument allowlist (Section 10).

8.4 Defense in depth and residual risk

• A theme's role could, in principle, change in the short window between the gateway's final check and the push finishing (for example, if someone publishes it in the Shopify admin at that exact moment). This cannot be fully eliminated from outside Shopify.
• To keep the window small: the role check runs immediately before the push, pushes contain only changed files, and nothing else runs between check and push.
• Because the app never passes "--allow-live" and runs the CLI non-interactively, Shopify CLI's own live-theme confirmation acts as a second, independent guard.
• After every push, the gateway fetches the theme list again. If the target's role changed, the app stops all further writes to that theme, records an incident, and tells the user in plain language what happened and what was pushed.
• The documentation and README describe this residual risk honestly instead of claiming it is impossible.

9. Claude Code Integration

Claude Code acts only as a local theme-editing engine inside the agent container.

9.1 Inputs

Claude Code receives:

• The user's messages in the conversation.
• The workspace path (inside the container).
• Shopify theme editing guidelines.
• Allowed file patterns and the sensitive-file list.
• Prohibited actions.
• New validation problems during an automatic repair attempt.
• Notices from the host (for example, "the user undid the last step" or "the user declined edits to config/settings_data.json").

9.2 Allowed theme paths

assets/**
blocks/**
config/**
layout/**
locales/**
sections/**
snippets/**
templates/**

Files outside these paths are rejected by the runner and, authoritatively, by host intake. Some files inside these paths are sensitive and require user approval (Section 9.4). Some are blocked entirely (for example layout/checkout.liquid).

9.3 Claude Code must not receive

• Shopify tokens or Theme Access passwords.
• Store or storefront passwords.
• Credential-store values other than its own Anthropic credential.
• Deployment commands or the ability to run any command.
• Permission to publish or push themes.
• Access to anything outside the workspace.
• Network access beyond the Anthropic API.
• A generic instruction to operate the computer.

9.4 Sensitive files and the approval pop-up

Some theme files hold settings the merchant customizes in the Shopify theme editor, or affect every page. Editing them can overwrite the merchant's work.

Sensitive files (require approval)

• config/settings_data.json — "Your theme editor settings, such as colors, fonts, and section content."
• config/settings_schema.json — "The list of settings available in the theme editor."
• templates/*.json and templates/customers/*.json — "Page layouts and section content you set up in the theme editor."
• sections/*.json (section groups such as header-group.json and footer-group.json) — "Header and footer content you set up in the theme editor."
• layout/theme.liquid and other layout/*.liquid files — "The master layout used by every page of your store."
• locales/*.json — "Your store's text and translations, including edits made with 'Edit default theme content'."

Blocked files (never approvable)

• layout/checkout.liquid and any other checkout-related file.
• Anything outside the allowed theme paths.

When the pop-up appears

• Live: when Claude attempts to write or edit a sensitive file, the runner pauses the tool call and sends an approval request. The host shows the pop-up.
• Backstop: if host intake finds a changed sensitive file that has no recorded approval for this step, the same pop-up appears before anything is accepted.

Pop-up content

• Title: "Approve changes to important theme files?"
• Message: "Claude wants to change files that control settings you may have customized in the Shopify theme editor. Changing them could overwrite those customizations."
• A list of every affected file, each showing the file name (for example, config/settings_data.json) and its plain-language description from the list above.
• An optional "Show what will change" expander.
• Two buttons: "Approve" and "Decline".
• "Decline" has default keyboard focus. Pressing Escape or closing the pop-up counts as Decline.

Outcomes

• Approve: the approval (file names, session, step, timestamp) is recorded in SQLite and the edit proceeds. The review screen and change history show that sensitive files were changed with approval.
• Decline: the edit is refused and nothing is written to those files. Claude is told the user declined and is asked to complete the request without changing those files, or to explain in plain language why it cannot.

9.5 Automatic repair loop

• After each step, if Theme Check reports new blocking problems (Section 13.3), the host automatically sends only those new problems back to Claude as a repair request. The user does not need to approve this.
• Maximum of 2 repair attempts per step.
• The progress area shows "Fixing a problem I found…" during repair.
• Each repair attempt goes through intake, sensitive-file approval, and Theme Check like any other step.
• If the problems remain after the final attempt, the host restores the workspace and candidate tree to the last good step and shows: "I couldn't make this change without errors. Your theme hasn't changed." Options: "Try describing it differently" or "Undo this step".
• Saving a change still requires a passing validation result and explicit user confirmation.

9.6 System instructions

Claude Code is instructed to:

• Make only the requested storefront change.
• Preserve existing behavior unless necessary.
• Keep Shopify Liquid and schema JSON valid.
• Not delete files.
• Avoid checkout, analytics, tracking, app embeds, and credentials.
• Avoid sensitive files unless the change genuinely requires them.
• Reuse existing theme patterns.
• Keep changes minimal and reversible.
• Ask the user a short clarifying question when a request is ambiguous, instead of guessing.
• Finish each step by reporting a plain-English summary, warnings, and the page types likely affected.

9.7 Execution and what the host trusts

The agent runner streams structured events (progress, messages, approval requests, questions, step results, errors, duration) to the host.

The host derives every fact it acts on from Git and the filesystem, not from Claude's own report (Section 11.5). Claude's summary and warnings are shown to the user, clearly labeled as Claude's description. Claude's suggested page types are used only as screenshot hints, after validation against known page types.

Claude Code never performs any Shopify operation.

10. Shopify CLI Integration

Only the Shopify write gateway (for writes) and the Shopify read service (for reads) in the trusted main process may start a Shopify container.

Authentication

• The store connects with a Theme Access password (created through Shopify's Theme Access app), which grants theme access only. Setup walks the user through obtaining it.
• The password is stored in safeStorage and delivered to each Shopify container over standard input, as described in Section 6.3. The store domain is passed as a non-secret setting.

Allowed operations (with the only permitted flags)

• List themes: structured JSON output.
• Pull a theme: by immutable theme ID, into the empty inbox/.
• Create an unpublished theme: the "unpublished" option with an app-generated name, structured JSON output so the new theme ID is captured.
• Create or reuse the preview development theme: the "development" option, structured JSON output.
• Push to a verified writable theme: by immutable theme ID, from read-only canonical/, with "nodelete" always set and an explicit "only" file list containing exactly the changed files. A full mirror push (without "only") is allowed only to the app's own preview theme.
• Theme Check: from a read-only tree, with the application's own configuration file, JSON output, no network, no credential.
• Preview URLs: constructed by the main process, never taken from CLI or model output.

Forbidden operations

• Publish a theme.
• Push to the live theme.
• Pass "--allow-live" or any live-override flag.
• Delete themes or delete remote files.
• Rename, share, or open a console or dev server.
• Read configuration from the theme directory (for example shopify.theme.toml). All settings are passed explicitly, and such files are rejected by intake anyway.
• Run any Shopify CLI command supplied by the user or the model.

Every invocation of the container runtime and of the CLI inside it uses an argument array, never a shell-interpolated string.

11. Git and Local History

Git is a local history, diff, and merge engine only. The app never configures remotes, never clones from or pushes to any server, and never interacts with GitHub. Any local Git capability that helps the core workflow (branches, squash merges, three-way merges, reverts, diffs, temporary indexes) may be used freely.

11.1 One repository per theme

• Each theme the app tracks has one Git repository, keyed by store ID and theme ID, stored in history.git/ outside the working tree.
• A new working copy created after a publish cycle starts from the retired theme's repository history, keeping history continuous.

11.2 Branches

• shopify: always represents what is believed to be on Shopify for this theme.
• session/<session-id>: the in-progress change, one commit per successful conversation step.
• undo/<change-id>: an in-progress undo.

11.3 Commit types

• sync: a fresh pull from Shopify (initial snapshot, drift check, or live-theme sync check). Created from inbox/ using a temporary index, so it never disturbs an active session's checkout.
• turn: one successful conversation step on a session branch.
• change: a saved change, squash-merged onto the shopify branch. One commit per saved change, so it can be reverted as a unit.
• revert: an undo of a saved change.

Example history on the shopify branch:

sync: pulled live theme 123456 for new working copy
change: make the announcement bar green
sync: theme editor edits detected in config/settings_data.json
change: add a free-shipping banner to product pages
revert: undo "make the announcement bar green"

11.4 Change record (SQLite)

Each saved change records:

• Change ID and session ID.
• Store identifier.
• Target theme ID and name.
• Origin theme ID (the live theme a working copy came from).
• The conversation (user messages and Claude summaries).
• Changed files (derived from Git).
• Sensitive-file approvals.
• Git commit IDs (turns, change, any merge).
• Validation result, including the baseline comparison.
• Screenshots (stored as local files, referenced by path).
• Save timestamp.
• Preview URL.
• Application and pinned tool versions.

11.5 Facts come from Git and the filesystem

The host computes, never trusts from Claude:

• Which files were added, modified, or deleted.
• Whether a file is binary, its size, and its type.
• The diff shown in the advanced view.
• The exact list of files passed to "only" when pushing.
• Whether sensitive files were touched.

Deleted files are not propagated to Shopify in the MVP. If intake detects a deletion, the file is restored from canonical/ and the user is told.

11.6 Git hardening

• The Git directory is separate from the working tree and never mounted into any container.
• Hooks are disabled for every Git call (hooks path set to an empty app-owned directory).
• System and global Git configuration are ignored; the app supplies its own minimal configuration and a fixed local identity ("Shopify Builder").
• Symlinks, file-system monitors, and attribute-driven filters are disabled. .gitattributes and any other dotfiles are rejected by intake before they can reach the working tree.
• Git only ever operates on canonical/, whose contents have passed intake.

12. Sync and Drift Protection

Merchants and installed apps can change a theme in Shopify at any time (most often config/settings_data.json and templates/*.json through the theme editor). The app must never silently overwrite those changes.

Before every save and every undo save:

1. Pull the target theme fresh into inbox/.
2. Run intake on the pulled files.
3. Create a sync commit on the shopify branch if anything differs from the previous sync.
4. If nothing changed on Shopify, continue.
5. If Shopify changed only files this session did not touch, continue. Because pushes are limited to the session's changed files with "nodelete", the Shopify-side changes are preserved.
6. If Shopify changed files this session also changed, merge the shopify branch into the session branch.
   • Clean merge: re-run Theme Check and refresh the preview, then ask the user to confirm again before saving.
   • Conflict: stop. Show "This theme was changed in Shopify while you were working, in the same places your change affects." Offer "Redo my change on the latest version" (starts a new step with Claude on the merged starting point) or "Cancel".

The same drift approach is used by the live-theme sync check in Section 7.6.

13. Validation Pipeline

13.1 File intake (every file entering trusted storage)

Intake runs on Shopify pulls (inbox/) and on every Claude step (workspace/). It scans the actual files on disk, not just what Git reports, so ignored or hidden files cannot slip through.

Intake rejects:

• Any path outside the allowed theme paths.
• Any dotfile or dot-directory anywhere, including .git, .gitattributes, .shopifyignore, .theme-check.yml, and .claude.
• Root-level configuration files such as shopify.theme.toml, package.json, or CLAUDE.md.
• Symlinks, hard links, device files, and anything that is not a regular file.
• Paths that escape the theme directory.
• Files above per-type size limits.
• Text files that are not valid UTF-8.
• Credential-like content.
• Blocked files (Section 9.4).
• Deletions (restored, see Section 11.5).

Intake requires a recorded approval for every changed sensitive file (Section 9.4).

Rejected files are restored from canonical/ in the workspace, and the user and Claude are told in plain language.

13.2 Per-step checks

1. File intake.
2. Sensitive-file approval check.
3. Parse every changed JSON file.
4. Copy accepted files into a candidate tree (canonical/ plus this step's changes).
5. Run Theme Check on the candidate tree.
6. Compare with the baseline.
7. Automatic repair if needed (Section 9.5).
8. Commit, push to preview, capture screenshots.

13.3 Theme Check baseline

Many themes, including popular third-party themes, already have Theme Check offenses. Blocking on those would block every change.

• A baseline Theme Check runs on every sync commit and is stored with that commit.
• Offenses are compared by check name, file, and message (not line number, which shifts as files change).
• A step is blocked if it introduces new error-level offenses, or any Liquid or JSON parse error in a changed file.
• New warnings are shown but do not block.
• Pre-existing offenses are hidden by default, with an "Existing issues in this theme" expander.
• Theme Check always uses the application's configuration file, never one from the theme.

13.4 Before saving

1. All per-step checks passed for the latest step.
2. Drift check (Section 12).
3. Shopify gateway verifies the target is writable.
4. User confirms.

A failed validation always blocks saving.

16. Typed IPC Surface

Long-running work is owned by the main process as jobs. Requests that start work return a job reference immediately; progress and results arrive as pushed events. The renderer is a projection of main-process state.

Request operations (narrow, schema-validated)

• Get setup status; run a setup step.
• Connect store; get connection status.
• List themes (already classified as save-target or read-only).
• Create working copy; create named copy; adopt theme (requires confirmation token from the confirmation dialog).
• Start change session; send message; answer question; respond to sensitive-file approval (approve or decline); undo step; save session; discard session.
• Cancel job; get job snapshot.
• Open preview (by theme ID; main constructs the URL); open Shopify Themes admin page.
• Run go-live readiness check; bring in live changes.
• List history; start undo of a saved change.
• Subscribe to events; unsubscribe.

Pushed events

• Job progress, job completed, job failed, job cancelled.
• Session assistant message, session question asked, session approval requested, session step completed, session preview ready.
• Theme role changed, working copy went live, safety incident.

Event rules

• Every event carries a job or session ID and an increasing sequence number.
• After a reload or reconnect, the renderer fetches a job snapshot and resumes from the latest sequence number.
• Events never contain secrets or absolute host paths.
• TanStack Query is used for request/response data; pushed events update its cache.

Jobs

• Job states are persisted in SQLite so an interrupted job (for example, the app closed during a save) is detected and reconciled on the next start, by re-pulling the target and comparing it with the expected Git state.
• A per-theme lock prevents two jobs from changing the same theme at the same time.
• A single-instance lock prevents two copies of the app from running.

Never expose operations such as:

• Run an arbitrary command.
• Execute shell input.
• Push to a theme with caller-supplied flags.
• Start a container with caller-supplied arguments or mounts.

17. Local Data

SQLite stores durable structured state:

• Store connection metadata (non-secret).
• Theme cache and theme ownership registry (kind, created by app, adopted, retired, origin theme, lineage).
• Change sessions, steps, and conversation.
• Sensitive-file approvals.
• Jobs and their states.
• Git commit references.
• Validation results and baselines.
• Save and incident records.
• Screenshot file references.
• Pinned image digests and tool versions.
• Application settings.

Secrets (Theme Access password, Anthropic credential, storefront password) remain in safeStorage. SQLite stores only non-secret references and metadata.

18. Electron Security Baseline

• Context isolation on, renderer sandbox on, Node integration off in every window.
• A strict Content Security Policy for the renderer.
• The preload exposes only the typed API in Section 16.
• Every IPC handler checks that the request came from the app's own window.
• In-app navigation and new windows are blocked.
• External links open only through the main process, and only for allowlisted Shopify domains (the store's myshopify.com domain and the Shopify admin).
• The screenshot window uses a separate, non-persistent session, no preload, sandbox on, navigation limited to the store's domain, and is never shown to the user as an interactive browser.
• Electron fuses: disable running as plain Node, disable Node options and inspect flags, enable ASAR integrity checking.
• Single-instance lock.

• "This theme was changed in Shopify while you were working."

22. Toolchain Bundling and Pinning

Target users cannot be expected to install Node.js, Git, Shopify CLI, or Claude Code.

• Git: bundled with the app through Dugite, at a pinned version.
• Shopify CLI (including Theme Check): bundled in the Shopify image at a pinned version.
• Claude Code: bundled in the agent image through a pinned Claude Agent SDK version.
• Node.js: bundled inside the images; the host app uses Electron's own runtime.
• Images are referenced by digest; the app verifies digests at startup.
• Upgrading any tool is a deliberate app release: bump the version, rebuild the image, run the contract tests that check CLI arguments and JSON output parsing, then ship the new digest.
• The only prerequisite the user installs is the container runtime (Podman preferred), and setup guides them through it.
• Setup then needs only the Shopify connection and the Anthropic connection.

25. Key Architectural Decisions

1. Electron over Tauri: easier orchestration of containers, Git, and file intake from a Node-based main process.
2. Local-first: no hosting requirement and credentials remain on the user's computer.
3. Container isolation: Claude Code runs in its own container with no shell, no Shopify credentials, and Anthropic-only network access; Shopify CLI runs in a separate short-lived container.
4. Copy-based handoff: files cross zones only through host intake; no directory is shared between the agent and Shopify containers, and Git is never mounted into any container.
5. Low overhead: one container runtime, three small pinned images, no always-on services.
6. Claude Code edits only: every Shopify operation stays in trusted application code behind a single write gateway.
7. Deny-by-default targets: only app-managed or adopted unpublished themes can be written; theme IDs, not names, are identifiers.
8. Repeated safety checks with defense in depth: roles are rechecked before and after every write, and the CLI's own live-theme guard is never overridden.
9. Visual review: changes are previewed on a hidden development theme with screenshots before anything is saved.
10. Conversational changes: a change is a session of steps, each one validated, previewed, and individually undoable.
11. Git-backed history: one repository per theme, one commit per saved change, reverts for undo, merges for drift.
12. Explicit saving: only preview pushes happen automatically; saving to an unpublished theme always needs the user's confirmation.
13. Manual go-live: the app prepares and checks, the user publishes in Shopify; publishing is absent from the product, command policy, and IPC surface.
14. Pinned, bundled toolchain: the user installs only a container runtime.
